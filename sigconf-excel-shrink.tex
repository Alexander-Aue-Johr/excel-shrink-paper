\begin{abstract}
  The German Federal Statistical Office (Destatis) publishes a multitude of Excel sheets containing statistical data. However, these files are often significantly larger than necessary due to unused cell formats, empty cells, and other inefficiencies, leading to increased storage requirements and slower data processing. In this paper, we introduce \textit{Excel Shrink}, an open-source tool that reduces the file size of these Excel sheets by up to 99.9\%. We analyze the root causes of the excessive file sizes, describe our method for identifying and eliminating redundant content, and compare our tool with existing solutions. Our evaluation on a comprehensive dataset of Destatis Excel files demonstrates substantial improvements in file size reduction without altering the visual appearance of the spreadsheets.
\end{abstract}

\section{Introduction}

Excel files are widely utilized as a format for data exchange across various domains, including finance, statistics, business, and research \cite{spreadsheet_usage_study}. Their versatility lies in Excel's capability to store tabular data, perform complex calculations, automate workflows using macros, and visually represent data through charts and graphs. This flexibility makes Excel indispensable in many organizations. However, as spreadsheets grow in complexity, significant challenges arise regarding file size and performance management \cite{spreadsheet_scalability}.

Unlike simpler formats such as CSV, which transparently display stored data, Excel files use a more complex structure. Excel employs the Office Open XML format, introduced in Excel 2007, where workbook contents are stored as a collection of XML files within a compressed ZIP archive \cite{office_open_xml}. This XML-based architecture enables advanced functionality, such as separating data from its presentation layer. For instance, Excel centralizes repeated strings in a shared string table, thus reducing redundancy by storing each text entry once and referencing it elsewhere in the workbook \cite{excel_internal_format}. Furthermore, formatting details—such as fonts, cell styles, and colours—are stored separately from the data itself in dedicated XML files, allowing Excel to reconstruct the sheet's visual appearance when it is opened \cite{xml_formatting_excel}.

\subsection{Excel’s Internal Storage Mechanisms}

To minimize file size, Excel makes extensive use of compression techniques. Once the workbook's data, styles, and structure are defined in XML, these files are bundled into a ZIP archive. The ZIP compression algorithm is particularly effective in this context due to the repetitive nature of XML tags and structures \cite{xml_compression_excel}. For example, in a large spreadsheet, tags like `<row>` and `<c>` (for cells) can appear hundreds of thousands of times. The compression algorithm identifies these repetitive patterns and encodes them with shorter representations, reducing the overall file size \cite{compression_algorithms}. Without compression, the verbosity of XML would result in substantially larger files.

Despite achieving considerable space savings, this approach introduces significant inefficiencies. The separation between the visible content seen by the user and the underlying storage structure can lead to scenarios where redundant or unused data continues to occupy considerable amounts of space in the file. These inefficiencies are not immediately apparent to users but can drastically increase file sizes, reducing the overall performance of both Excel and the systems that interact with it.

One common issue arises when users apply formatting to large ranges of cells that contain no actual data. For example, a user might highlight an entire row or column to change its font style or background colour, but only a subset of the cells are populated with data. The formatting persists across all selected cells, including those that remain empty, creating unnecessary XML records that Excel must store in its underlying files. As Excel stores formatting separately in its XML structure, each formatted but empty cell is treated as a separate entity, adding to the size of the workbook \cite{spreadsheet_practices}. This problem is exacerbated when users apply conditional formatting or intricate styles over vast areas, further bloating the file without any visible effect.

Similarly, duplicating entire sheets within a workbook can carry over both data and formatting, even when only a portion of the original sheet is needed. Users often duplicate sheets to retain formulas, styles, or layouts, but this also transfers unnecessary metadata and formatting definitions from the original sheet, including empty cells, unused rows, and hidden columns. These redundancies are copied wholesale, and in many cases, users do not realize that they are preserving and propagating unused content. Over time, as sheets are copied and modified, the workbook's file size balloons, with Excel continuing to store and manage a growing list of redundant elements that serve no practical purpose.
 
A less obvious but equally impactful inefficiency arises from Excel's approach to managing rows and columns. Excel maintains definitions for rows and columns even if they are not populated with data. For instance, if a user inadvertently applies formatting to an entire column but only uses a few cells, the column definition persists in the underlying XML. In some cases, we have observed Excel files where the maximum allowable number of rows and columns were defined, significantly inflating the file size without contributing any value. Although these rows and columns were not fully utilized with data, their definitions were still present in the file, unnecessarily consuming space. These excessive definitions often remain hidden from the user’s view, making them difficult to detect and remove manually.



These inefficiencies not only increase storage requirements but also degrade Excel’s performance. Larger files take longer to open, save, and modify. In enterprise environments, this can lead to significant delays when handling shared workbooks or automating data processing tasks through scripts and applications that interface with Excel. The excessive size of the files puts a strain on memory and processing resources, leading to a slower user experience and increased frustration in collaborative settings where files are frequently shared or integrated with other systems. These inefficiencies, therefore, represent a considerable challenge for users working with large datasets or managing multiple Excel files.

By addressing these issues—removing redundant formatting, eliminating unused rows and columns, and optimizing the internal XML structure—significant reductions in file size and performance improvements can be achieved. This is the key focus of our open-source tool, \texttt{excel-shrink}, which identifies and eliminates these inefficiencies while preserving the visual and functional integrity of the spreadsheet.

\subsection{Impact of File Bloat on Performance}

Excel file bloat—characterized by excessive file size without a corresponding increase in useful content—can severely impact performance \cite{excel_performance_issues}. Large files take longer to open, save, and process, whether accessed by human users or automated scripts. In enterprise environments, where Excel files are frequently shared, modified, and stored, these performance bottlenecks can disrupt workflows and reduce operational efficiency \cite{spreadsheet_workflow_disruptions}.
Our work with datasets from the German Federal Statistical Office (Destatis) exemplifies these performance challenges. The Excel files we analyzed contained substantial redundant content, including unused rows, columns, and formatting definitions, which contributed to their excessive size and slow processing times \cite{excel_storage_issues}. Some of these files exceeded several hundreds of megabytes in their uncompressed form, taking an unusually long time to open and save, both in Excel and through automated means.

\subsection{Analyzing Redundant Content in Excel Files}

Redundant content in Excel files manifests in various forms, each contributing to file bloat in different ways. The most prevalent types of redundancy include:

\begin{itemize}
    \item \textbf{Empty but formatted cells:} When users apply formatting (such as fonts, colours, or borders) to large ranges of cells, the formatting persists even in cells that contain no data \cite{spreadsheet_practices}. This results in thousands of empty cells consuming unnecessary space without any visible effect on the sheet's content.
    \item \textbf{Unused rows and columns:} Entire rows or columns may be defined within the workbook's XML structure despite containing no data. These unnecessary definitions contribute to bloating the file size \cite{spreadsheet_design_errors}.
    \item \textbf{Duplicated sheets:} Users often copy entire sheets for convenience, inadvertently duplicating redundant structures such as empty cells with formatting or hidden rows and columns \cite{spreadsheet_duplication}.
\end{itemize}

To quantify the impact of these redundancies, we performed a detailed analysis of Excel files from Destatis. Our investigation revealed that many files contained vast amounts of poorly structured or unused content that provided no functional benefit. In extreme cases, we discovered that worksheets contained definitions for rows and columns extending to Excel's maximum limits, despite containing no data. By removing these excess elements, we were able to reduce file sizes by as much as 99.99\% in some instances.

\subsection{Related Work on Excel File Optimization}

Several tools and techniques have been developed to mitigate Excel file bloat \cite{excel_optimization_tools}. These include commercial software, Excel add-ins, and built-in Excel features designed to remove redundant content and reduce file sizes. However, most existing tools have notable limitations. Many are restricted to processing a limited number of files or are constrained to specific Excel versions or enterprise environments \cite{excel_tools_comparison}. Furthermore, these tools either fail to remove all redundant content or inadvertently alter the sheet's visual appearance, making them unsuitable for users who need to preserve the layout of their workbooks \cite{excel_cleanup_tools}.

These limitations underscored the need for a more robust, scalable solution. To address this gap, we developed our open-source tool, \texttt{excel-shrink}, capable of processing large batches of Excel files while maintaining the integrity of the spreadsheet layout.

\subsection{Our Contribution: excel-shrink}

To combat the issues posed by file bloat in Excel, we introduce \texttt{excel-shrink}, an open-source tool written in Python designed to efficiently reduce the size of Excel files by removing redundant content \cite{excel_shrink_tool}. The tool conducts an in-depth analysis of the workbook's XML structure to identify and eliminate unnecessary elements, including empty but formatted cells, unused rows, and columns.

For users who prefer a user-friendly interface without the need to install Python or use command-line tools, we developed Excel Shrink UI. Built using Flutter for Windows and integrating the compiled Python script via Nuitka, this version enables users to optimize their Excel files through a simple and intuitive interface.

Unlike existing tools, \texttt{excel-shrink} is capable of processing unlimited numbers of Excel files, making it suitable for handling large datasets, such as the 1,182 files we analyzed from Destatis. The tool ensures that the visual layout of the spreadsheet is preserved, preventing the loss of important formatting. By automating the cleanup of redundant content, \texttt{excel-shrink} significantly reduces the time and effort required to optimize Excel files, making it an ideal solution for organizations dealing with large-scale spreadsheets.

In this paper, we present the technical foundations of \texttt{excel-shrink}, outline the methodology used to analyze Excel file bloat, and evaluate the tool's performance across the Destatis dataset. Our results demonstrate that \texttt{excel-shrink} can reduce file sizes by up to 99.99\% without compromising the usability or appearance of the Excel files.


\section{Scraping Destatis}

The Destatis website does not provide an API for searching publications, making it necessary to interact with the website directly. To automate this process, we developed a web scraper that searches for relevant publications while minimizing the number of requests to the server. Through extensive testing, we discovered that Excel files are exclusively found in the "Publication" document type. By using the GET parameter \texttt{documentType\_=publication}, we were able to significantly narrow down our search results.

Initially, we assumed that searching for the term \texttt{xlsx} would identify all publications containing Excel file attachments. However, this search only returned about 100 results, far fewer than the actual number of Excel files available on the Destatis website. Furthermore, there is no option to retrieve a complete list of all publications ever created. To overcome this, we refined our strategy by searching based on publication years. A publication should appear in the search results when queried by its publication year. Although this approach returns some irrelevant results—where the publication year might appear in the text or a file attachment—the number of requests is greatly reduced by caching and reusing links to the Excel file attachments. This ensures that the same files are not downloaded multiple times.

The search results on the Destatis website, like many others, are paginated, with the interface offering the ability to display 10, 12, or 30 entries per page. The number of results per page can be adjusted using the GET parameter \texttt{resultsPerPage=30}. While the interface does not provide an option for more than 30 results per page, we found that manually setting this parameter allowed us to request up to 100 results per page. Through testing, we confirmed that 100 is the maximum number of results that can be returned at once. We set the \texttt{resultsPerPage} parameter accordingly to reduce the number of requests further.

Once the results for a page are fetched by the web scraper, we simulate clicking the "next page" link to load subsequent results. The helper function \texttt{get\_next\_page\_url} handles this step, using the CSS class \texttt{forward button} to identify the link. The URL for the next page is extracted via the XPath expression \texttt{//a[@class='forward button']/@href}.

\begin{lstlisting}[caption={Function to retrieve the link to the next page}, label={lst:get_next_page_url}]
def get_next_page_url(html: str) -> str:
    xpath = "//a[@class='forward button']/@href"
    tree = etree.HTML(html)
    next_page = tree.xpath(xpath)
    if next_page:
        return next_page[0]
    return ""
\end{lstlisting}

The web scraping and downloading process is outlined in Algorithm \ref{alg:web_scraping_caching}.

\begin{algorithm}
  \caption{Web Scraping and Downloading Excel Files with Caching}
  \label{alg:web_scraping_caching}
  \begin{algorithmic}

      \STATE \textbf{Input:} Base URL \texttt{B}, form URL \texttt{F}, download folder \texttt{D}, CSV cache file \texttt{C}, crawl delay (30 seconds)
      \STATE \textbf{Initialize:} Cached URLs set \texttt{U}, and load file records from CSV \texttt{C}
      \STATE Create folder \texttt{D} if it does not exist

      \STATE \COMMENT{--- Scraping Process ---}
      \FOR{each year in years}
          \STATE Construct the search URL using year and base parameters
          \WHILE{there are more pages to fetch}
              \STATE Send HTTP GET request to search URL
              \STATE Parse HTML to extract \texttt{.xlsx} links
              \STATE Filter links that are not already in the cache \texttt{U}
              \FOR{each new link}
                  \STATE Extract file name from link
                  \STATE Add new link and file name to file records
                  \STATE Append new records to cache \texttt{C}
              \ENDFOR
              \STATE Save the updated file records back to CSV \texttt{C}
              \STATE Check for the next page button
              \IF{next page exists}
                  \STATE Update URL to the next page
                  \STATE Wait for \texttt{CRAWL\_DELAY} seconds
              \ELSE
                  \STATE Exit the loop
              \ENDIF
          \ENDWHILE
      \ENDFOR

      \STATE \COMMENT{--- Checking for Duplicate Filenames ---}
      \STATE Combine cached and new file records
      \STATE Check if there are duplicate filenames
      \IF{duplicates exist}
          \STATE Print warning and exit
      \ENDIF

      \STATE \COMMENT{--- Download Process ---}
      \FOR{each new file record}
          \STATE Download file from the URL
          \STATE Save it in the download folder \texttt{D}
          \STATE Wait for \texttt{CRAWL\_DELAY} seconds
      \ENDFOR
  \end{algorithmic}
\end{algorithm}

  \item \url{/SiteGlobals/Forms/Suche/Expertensuche\_Formular.html}:

  \item \url{templateQueryString=2000}:
  
  This query parameter specifies the search year. In this case, the search is focused on publications from the year 2000. By adjusting this value, different years can be searched.

  \item \url{gtp=474\_list\%253D2}:
  
  This parameter handles pagination. It points to a specific page of search results. The value \texttt{\%253D} is

  After decoding, the query parameter becomes \texttt{gtp=474\_list=2}. The number after the second equal sign corresponds to the current page index in the pagination of the search results.
  \item \url{documentType\_=publication}:
  
  This parameter filters the results by the type of document. By setting this to \texttt{publication}, the search is limited to publications, where Excel files are usually attached.

Once we have queried each publication year from 2000 to 2024, and the file attachments have been extracted from the result pages until no further "next page" button is available, the scraping process for the Excel files is complete.

\subsection{Respecting Crawl Delay}

To minimize the load on the Destatis website, we adhered to the crawl-delay directive specified in the site's \texttt{robots.txt} file, pausing for 30 seconds between requests. This delay ensures that our scraper operates within the guidelines provided by Destatis.


\section{Excel Shrink}

Die Aufgabe von Excel Shrink ist es die Größe von Excel-Dateien zu reduzieren, indem es Inhalte entfernt, die für den Nutzer unsichtbar und daher vermutlich nicht absichtlich ihren Weg in die Datei gefunden haben. Dazu zählen unter anderem leere Zellen, Zellen mit Whitespaces, oder Zellen mit einem Format, welches für den benutzer nicht sichtbar ist, sowie ungenutzte Zeilen und Spalten.

\subsection{Deletion of White Spaces}

Excel users lack a straightforward method to identify which cells in a worksheet contain only whitespace characters. To highlight these whitespaces, we have marked cells containing exclusively whitespaces in red within this worksheet, which includes 4,121 whitespace instances, as shown in Figure \ref{fig:whitespaces} \cite{destatis2023Konsumausgaben5811109}.

\begin{figure}[ht]
  \centering
  \includegraphics[width=\linewidth]{images/excel_shrink/whitespaces/whitespaces.png}
  \caption{Cells containing only whitespaces are highlighted in red.}
  \label{fig:whitespaces}
\end{figure}%

\begin{lstlisting}[caption={Cell D844 in sheet28.xml}, label={lst:whitespaces_d844}, firstnumber=48]
  <row r="844" spans="1:16" ht="14.1" customHeight="1">
    <c r="D844" s="428" t="s">
        <v>102</v>
    </c>
\end{lstlisting}
To detect these whitespaces, it is insufficient to examine the cell itself, as even a single space is stored by Excel in the file for recurring texts, even if the text appears only once in the entire Excel file. Cell D844 appears in the XML as shown in Listing \ref{lst:whitespaces_d844}.

The row is marked by the \texttt{<row>} tag and has the attribute \texttt{r="844"}, indicating that it is the 844th row. Within the row, the \texttt{<c>} tag represents a cell, identified by the attribute \texttt{r="D844"}. The attribute \texttt{t="s"} specifies the cell type; in this case, \texttt{s} stands for "String," meaning the cell's content is interpreted as a string \cite{openxml}.

The cell's value is stored within the \texttt{<v>} tag, where the value \texttt{102} is specified. This value is interpreted as an index in a string table, referencing a specific text in a separate list defined in the Excel file, namely the sharedStrings.xml file.
To locate the value, we must search for the \texttt{sst} node in the sharedStrings.xml file, as shown in Listing \ref{lst:sharedStringsSst}.

\begin{lstlisting}[caption={Shared String Table (sst) in sharedStrings.xml}, label={lst:sharedStringsSst}, firstnumber=48]
  <sst count="17962" uniqueCount="732">
    <si>
        <t>062</t>
    </si>
\end{lstlisting}

The provided XML excerpt displays a portion of the Shared String Table (SST) in an Excel file. The abbreviation \texttt{sst} stands for \textit{Shared String Table}. The Shared String Table is a structure that allows for the storage and management of shared strings within an Excel workbook. Instead of storing each string separately in every cell, each unique string is stored once in the Shared String Table. This approach saves storage space, as cells then reference these strings via indices. Each entry in this table has an ascending index number, starting at 0 for the first string, 1 for the second, and so forth. In this example, the \texttt{<sst>} element represents the entire table, which in this case has attributes \texttt{count="17962"} and \texttt{uniqueCount="732"}.

\begin{lstlisting}[caption={Shared String Item (si) in sst}, label={lst:whitespacesSi}, firstnumber=48]
<si>
  <t xml:space="preserve"></t>
</si>
\end{lstlisting}

The \texttt{count} attribute indicates the total number of strings in the table, while \texttt{uniqueCount} represents the number of unique strings. In this case, there are 17,962 strings in total, of which 732 are unique. This means that many strings in the table are used multiple times.

Within the SST, there are elements of type \texttt{<si>} (Shared Item), each containing a string. In this example, the \texttt{<t>} element displays the actual text of the string stored in the table. Here, the string \texttt{062} is represented, which can be referenced by an index in a cell.

To find the 102nd index, we must look for the 103rd entry, which is shown in Listing \ref{lst:whitespacesSi}.

\begin{lstlisting}[caption={Empty string at index 102 in sst}, label={lst:whitespacesSi}, firstnumber=48]
<si>
  <t xml:space="preserve"></t>
</si>
\end{lstlisting}

Within the \texttt{<si>} element is a \texttt{<t>} element containing the actual text of the string. In this specific case, the content of the \texttt{<t>} element is empty, indicating that no text is stored. The attribute \texttt{xml:space="preserve"} suggests that this represents a whitespace character. Therefore, all cells referencing index 102 for the reusable string can be deleted, as the whitespace is not visible.

Each \texttt{<col>} declaration contains specific information about one or more columns. The first five \texttt{<col>} definitions relate to the data range. However, the last definition, \texttt{min="10" max="18"}, pertains to a redundant range. This section defines columns that lie outside the actual data range in the worksheet, specifically columns starting from column J, thereby representing unnecessary or unused definitions.

  <col min="16148" max="16384" width="8.77734375" style="39" customWidth="1" />
</cols>
\end{lstlisting}

The first column \texttt{min="16146" max="16146"} has a fixed width of 2.21875 and refers to column WVZ, which is visible in Figure \ref{fig:col_w} as the column immediately to the left of WWA but is too narrow to display more than the letter "W." The second column \texttt{min="16147" max="16147"} defines column WWA with a width of 5.21875. The final definition \texttt{min="16148" max="16384"} covers a larger range from column 16,148 to 16,384, corresponding to columns WWB through XFD, assigning a width of 8.77734375 to these columns. This explains why scrolling all the way to the right via the scrollbar lands on column WWB. The penultimate definition specifies where the data range ends, thereby also defining where the scrollable range ends, and the final definition simply assigns a default width to all remaining columns. Surprisingly, these column definitions appear to extend indefinitely, seemingly only terminating at Excel's defined maximum limit of 16,384 columns. We have no explanation for why these user-defined column widths appear just before the maximum allowable column limit, but not exactly at it.

To delete these columns, the following steps must be taken:
1. Identify the actual right boundary of the data range and cell formats.
2. Determine the first redundant column definition and save the "min" value um sie später zu verwenden.
3. Delete all redundant column definitions except for the last one.
4. Overwrite the "min" value of the last column definition with the stored value of the first redundant column definition.

Following these steps is crucial. We experimented with merely deleting the excess columns without ensuring that the last column definition extended to the final possible column (16,384), but this caused Excel to mark these worksheets as corrupted and perform certain repairs. Part of these changes included altering the default row height, resulting in some worksheets appearing visually altered, as shown in Figures \ref{fig:hidden_columns_before} and \ref{fig:hidden_columns_after}. On the left is the original, and on the right is the repaired version by Excel. For instance, row 6 has changed in height due to the repair, causing visible shifts in the worksheet. Correctly deleting column definitions while ensuring the last column definition extends to the column limit of 16,384 prevents this error.

Some of the worksheets we examined contained vast numbers of cells without any content. The most extreme case was a worksheet with 8,141 cells containing values and 5,237,075 cells without values, meaning that only 0.15\% of the stored cells actually had a value \cite{destatis2023Rechnungsergebnisse}[Sheet "csv-71717-25"].
Listing \ref{lst:cellsCsv7171725End} shows the last row of this worksheet.

\begin{lstlisting}[caption={The last row in the worksheet csv-71717-25}, label={lst:cellsCsv7171725End}]
  <row r="1048576" spans="3:7" ht="12.75" customHeight="1">

Unlike the whitespaces, these cells now contain no value and therefore do not need to be cross-referenced with the sharedStrings file. However, it is possible that such empty cells may have a background color assigned, as is the case with some cover sheets used for page design or for highlighting table headers. Additionally, these cells might have borders applied.

To determine this, one must examine the \texttt{s} attribute, which stands for the style index applied to the cell. The values \texttt{s="538"}, \texttt{s="537"}, and \texttt{s="541"} correspond to indices in a lookup table where all cell styles are stored. The styles matching these style indices can be found in the xl/styles.xml file. The relevant excerpts are shown in Listing \ref{lst:cellXfsCsv7171725}.

\begin{lstlisting}[caption={Cell styles in styles.xml for csv-71717-25}, label={lst:cellXfsCsv7171725}]
<cellXfs count="778">
  <!--538-->
  <xf numFmtId="0" fontId="0" fillId="0" borderId="0" xfId="0"/>
  <!--539-->
  <xf numFmtId="0" fontId="4" fillId="0" borderId="0" xfId="3" applyNumberFormat="1" applyFont="1"/>
  <!--542-->
  <xf numFmtId="0" fontId="1" fillId="0" borderId="0" xfId="1" applyNumberFormat="1" applyFont="1" applyAlignment="1">
    <alignment horizontal="right"/>
  </xf>
\end{lstlisting}

The XML structure within \texttt{<cellXfs>} contains formatting properties defined for cells in an Excel file. Each \texttt{<xf>} element represents a formatting rule. Similar to the Shared Strings file, formatting rules are indexed based on their order in the list, starting with the first at 0, the second at 1, and so on. For the IDs \texttt{s="538"}, \texttt{s="537"}, and \texttt{s="541"}, one must look for the 538th, 539th, and 542nd elements in the list, respectively. The attributes control the cell's appearance. The \texttt{numFmtId} attribute specifies the number format used for the cell, while \texttt{fontId} describes the font ID. \texttt{fillId} refers to the fill color, and \texttt{borderId} defines the border properties. \texttt{xfId} references a format template from which the cell inherits properties. The attributes \texttt{applyNumberFormat}, \texttt{applyFont}, and \texttt{applyAlignment} indicate whether the corresponding number format, font, and text alignment are applied to the cell. If the \texttt{alignment} element is present, it specifies the text alignment within the cell, such as right alignment. This structure defines the formatting rules used for the display and layout of the cell contents.

Inspection of these styles reveals that these cells only apply styles that are not visible for empty cells. They use different fonts, and cell G1048576 is additionally right-aligned. Therefore, all these cells are redundant and can be deleted accordingly.

Another case arises when the formatting rules include borders. As a user one does not have any means to identify that by looking at the sheet. All the visible cells had the overriden fill color. and the rest of the cells were hidden behind hidden columns. Only after unhiding those columns the error becomes evident. Errors like that make preserving the visual apaerance especially diffuciult.

We can't just decide to delete all cells that have  a style applied that tells the cell to aplly no fill. because such a scenario might be usfull in some sutuations. For exaple if the whole row or column is intedet to have a certain style and only some cells should apply no style as an exception to the rule. At the ssame time in some scenarius that might not be intedet and the file is exceptionally large, because some rows got accadentially a style applied and all cells in those rows up until the limit of possible columns in that row define, that this style should be overridden by no style.

Um die Dateigröße trotzdem zu verringern und solche änderungen an der darstellung zu verhindern gehen wir folgendermaßen vor. Wir ermitteln zunächst den Style der Spalte und der Zeile in der sich die Zelle befindet. Hat entweder die Spalte oder Zeile eine Hintergrundfarbe definiert, so überprüfen wir ob die Zelle dieselbe Hintergrundfarbe definiert. In diesem Fall löschen wir die Zelle. Zeile ab, behalten wir die Zelle.

\section{Deletion of Empty Rows}

Similar to cells ohne Inhalt aber mit sichtbarem Format, rows can also contain no defined cells aber dürfen trotzdem nicht gelöscht werden, weil sie beispielsweise eine definierte Höhe haben. If a row is deleted, the following issue, depicted in Figure \ref{fig:cell_borders_row_height_fail} compared to the original Figure \ref{fig:cell_borders_row_height_original}, occurs. The spacing between the header and the table shrinks because the intermediate row, which served as spacing between the header and the table, is deleted, and the default row height for the worksheet is applied, which is smaller than the custom height of the row. Diese Zeile sehen wir in Listing \ref{lst:rowWithCustomHeight}.
\begin{lstlisting}[caption={}, numbersep={-7pt}, label={lst:rowWithCustomHeight}]
  <row r="2" spans="1:12" ht="8.25" customHeight="1">
\end{lstlisting}
Das Attribut customHeight bedeutet, dass diese Zeile eine benutzerdefinierte Höhe zugewiesen wurde, und diese Höhe steht in dem \texttt{ht} attribute: 8.25  Diese Zeile darf also nicht gelöscht werden. Allerdings fanden wir bei der untersuchung der Arbeitsblätter aber auch viele, welche eine immense Anzahl an leeren Zeilen enthielten, die jedoch eine benutzerdefinierte Höhe hatten und damit nicht gelöscht werden dürfen.
In dem extremsten Fall in unserer Analyse enthielt ein Arbeitsblatt 1048576 definierte Zeilen von denen 1048480 Zeilen eine definierte Höhe hatten aber außerhalb des Bereichs mit Daten lagen. \cite{destatis2022Wanderungen}[Sheet "Tabelle 1.2.1"].
Nur 94 Zeilen hatten Inhalt, was 0.00009\% entspricht. Die letzte Zeile ist in Listing \ref{lst:lastRow} dargestellt.
\begin{lstlisting}[caption={}, label={lst:lastRow}]
<row r="1048576" ht="12.75" hidden="1" customHeight="1"/>
\end{lstlisting}
Die 1048480 Zeilen über dieser Zeile sind identisch mit außnahme der \texttt{r} attribute. Sie haben alle die gleiche Höhe und es handelt sich um versteckte Zeilen, da das Attribut hidden="1" haben. Obwohl sie dem Benutzer nicht angezeigt werden haben sie eine benutzerdefinierte Höhe von 12.75 Einheiten, weshalb sie dennoch in der Datei gespeichert sind. Die Zeile 1048576 entspricht auch der letzten Zeile, die durch das Maximum von 1048576 Zeilen in Excel möglich sind. Würde Excel eine Höhere Anzahl an Zeilen erlauben, wäre der dadurch verschwendete Dateispeicher als noch deutlich höher. 

Wir können uns nicht darauf verlassen, dass eine Zeile einfach nur keine definierte Höhe haben muss, damit wir sie löschen können. Trotzdem können wir nicht einfach Zeilen löschen, die eine benutzerdefinierte Höhe haben, da sie möglicherweise für das Layout des Arbeitsblatts wichtig sind. Daher müssen wir eine andere Methode finden, um leere Zeilen zu identifizieren, die gelöscht werden können.
To ensure that deleting empty rows does not alter the worksheet's visual representation, we adopt a strategy similar to that used for removing columns. First, we determine the actual range where values, background colors, or borders are defined. Then, we iterate through all empty rows and delete them only if they lie outside this range. This approach allows us to significantly reduce the file size of some worksheets without altering their content or appearance.

\subsection{Ausgabe der Reduktionsergebnisse}

Schließlich berechnen wir noch den Prozentualen Anteil der Reduktion an der ursprünglichen Größe. Diese Diese ergebnisse werden zum Schluss in einer csv Tabelle gespeichert.

\section{Related Work}

\subsection{NXPowerLite Desktop}
The program NXPowerLite Desktop is a commercial software \cite{nxpowerlite_desktop}. A 14-day trial version is available. Although the primary purpose of the program is to reduce the file size of Excel files by compressing embedded images, it also removes some, but not all, empty cells. However, it ignores all cells containing only whitespaces, redundant column definitions, and unnecessary rows.
The program has limited batch functionality, allowing the selection and reduction of multiple files simultaneously, but this is restricted to a maximum of 20 files.

\subsection{Inquire Add-in}

Inquire is an add-in for Excel, available exclusively for Excel versions within Office Professional Plus and Microsoft 365 Apps for Enterprise. Other versions, such as Office Home, Microsoft 365 Family or Single, and Microsoft 365 Business, do not support this add-in.

To activate the add-in, the following steps must be taken. Navigate to the File menu and select Options. This opens a dialog, where one clicks on Add-ins.
In the "Manage" dropdown, select "COM Add-ins", and then click on "Go...".
In the subsequently opened dialog, the Inquire Add-in can be activated. If the Inquire Add-in does not appear in the dialog, it is due to the use of an incorrect version of Excel.

Compared to our solution, Inquire ignores whitespace cells but successfully deletes empty cell, column, and row definitions; however, in certain instances, a substantial number of these elements remain undeleted. Furthermore, whitespace cells are entirely ignored. For instance, in a worksheet used as a cover sheet, only 77 rows were utilized, and all rows from row 78 onwards were hidden. \subsection{Excel Performance Tab}

Since 2022, Excel for Web has included a new feature named \textit{Check Performance}, and since 2023, this feature has also been available in Excel for Windows. It can be accessed through the "Review" tab in the Ribbon menu. In our comparison with alternative tools, this function achieved the largest reduction in file size; however, it failed to remove unneeded column definitions and Cells with Whitespaces.

However, Check Performance was also capable of outperforming Excel Shrink in specific cases without altering the worksheet’s appearance. Nevertheless, it modified the worksheet in a manner that required users to perform multiple steps to revert the changes made by Check Performance. This issue arose when a worksheet contained an actual value in a hidden row, and between this row and the next visible row, there were hundreds of thousands of additional hidden rows without any values. Zum beispiel hatten wir eine Arbeitsblatt, dessen Bereich mit sichtbaren Zeilen ging bis Zeile 94 und nachdem wir die unsichtbaren Zeilen sichtbar machten um zu verifizieren was wir bereits beim untersuchen der xml datei des sheets bemerkt hatten: In der Zeile 65536 in Spalte A war die Zahl "3" gespeichert, die vermutlich durch ein versehen dort hingeraten ist.\cite{destatis2022Wanderungen}[Sheet: "Tabelle 2.1.1"].

In such scenarios, Excel Shrink is unable to remove the hidden rows because our strategy involves removing only content outside the range of actual values and visible formatting. Since the last row within the user-designated area contains an actual value, all intervening rows must be preserved. In contrast, Check Performance removes all these hidden rows. This action alone would typically result in the previously hidden and now deleted rows becoming visible again. To prevent this, Check Performance employs a workaround by setting the row height to zero for the entire worksheet. This creates the illusion that the rows are deleted, when in fact they are merely not visible due to having no height.

However, this approach presents a significant drawback for users. Once users select all rows and attempt to make them visible again, the deleted rows remain invisible. To actually make all rows visible, users must select all rows in the worksheet and assign a new height. This method is disadvantageous because it also alters the height of rows that users may have previously customized. To preserve these custom height settings, users must follow a specific procedure: first, select all rows using the Select All button, then hold down the Control key and deselect all visible rows except the last one. Consequently, only the last visible row and all hidden rows remain selected. Users can then adjust the height of all previously invisible rows using the resize handle of the last visible row, thereby making them visible again.

Given that users may be surprised when attempting to make the rows visible in the usual manner but find that the rows remain hidden, and considering that the steps required to actually make these rows visible involve a learning curve and can be time-consuming—especially when the worksheet already contains several visible cells requiring multiple scrolls to deselect the hidden rows—we decided not to adopt the same strategy as Check Performance. Instead, we opted to retain these rows to avoid imposing additional complexity and inconvenience on the user.

Additionally, Check Performance removed cells and rows that did alter the visual appearance of worksheets. For example, the cover sheet shown in Figure \ref{fig:performance_before} was modified such that the cells responsible for whitespace on the cover sheet were removed, as illustrated in Figure \ref{fig:performance_after}.\cite{destatis2022Verkehrsunfaelle}

\section{Conclusion}
\label{sec:conclusion}

We have presented \textit{Excel Shrink}, an open-source tool that significantly reduces the file sizes of Excel sheets from Destatis by eliminating unnecessary content. Our analysis identified common practices that lead to bloated Excel files and demonstrated how targeted removal of redundant data can achieve reductions of up to 99.9\% without altering the spreadsheets' appearance.


Our tool outperforms existing solutions in both file size reduction and preservation of formatting. By making \textit{Excel Shrink} available to the community, we hope to facilitate more efficient data processing and analysis of large-scale Excel datasets.
